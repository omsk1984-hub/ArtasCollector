# Кириллица при вложенном выполнении `.ps1` — результаты проверки

Проверка: как ведёт себя вывод кириллицы, когда один PowerShell-скрипт
вызывает другой (вложенный `.ps1`). Скрипты `run_Writer.ps1`,
`run_Reader.ps1`, `run_Stat.ps1` и др. запускаются именно так — либо напрямую,
либо внутри `pwsh -Command`.

## Как проводилась проверка

Создавались временные debug-скрипты в `scripts/`:

- внешний вызывает внутренний через оператор `&` (как в реальных `run_*.ps1`);
- отдельные варианты — где внутренний скрипт сам выставляет
  `[Console]::OutputEncoding = UTF8`, и где не выставляет;
- отдельные варианты — где внутренний вызывается отдельным процессом
  `pwsh -File`.

Все запускались в двух окружениях:

1. **Под UTF-8-префиксом** (как предписано в `.roo/rules-code/02-powershell.md`):
   ```
   pwsh -NoProfile -Command "[Console]::OutputEncoding=[Text.Encoding]::UTF8; $OutputEncoding=[Text.Encoding]::UTF8; chcp 65001 > $null; & '<script>.ps1' -NoPause"
   ```
2. **Без префикса** — консоль родителя в CP866:
   ```
   pwsh -NoProfile -ExecutionPolicy Bypass -File "<script>.ps1" -NoPause
   ```

## Результаты

### Тест 1 — UTF-8-префикс у внешнего вызова, вложенность через `&`

Кириллица **корректная** на всех уровнях:

```

[outer] Console.OutputEncoding = utf-8
[inner] Проверка кириллицы: Привет, мир! Ёжик, щука, ёлки.
[inner/dotnet] Кириллица из вложенного процесса: ЁЖИК-ЩУКА-ЁЛКИ

```

```

[outer5] ��᫥�㥬�� ��ਫ���: 𦨪, �㪠.
```

## Причина (модель)

1. **`& script.ps1` внутри того же хоста.** Вложенный скрипт исполняется в
   **том же** .NET-хосте PowerShell и пишет в **общий консольный handle**
   родителя. Кодировка вывода фиксируется при старте .NET-хоста; смена
   `[Console]::OutputEncoding` внутри того же хоста **не переоткрывает**
   выходной поток. Поэтому если родитель в CP866 — кириллица ломается, и
   собственная настройка кодировки вложенного скрипта бесполезна.

2. **`pwsh -File script.ps1` (отдельный процесс).** Открывается новый
   консольный handle. Здесь установка UTF-8 внутри скрипта **работает**,
   даже если родитель в CP866.

3. **Дочерние .NET-приложения** (`dotnet run` / `dotnet <dll>`) — это
   отдельные процессы со своим `Console.OutputEncoding`, независимым и от
   родителя, и от PowerShell-скриптов. Их вывод лечится **только внутри C#**
   (`Console.OutputEncoding = System.Text.Encoding.UTF8;`), как и описано в
   `.roo/rules-code/02-powershell.md`.

## Кодировка и логи (Writer / Stat)

**Влияет ли установка UTF-8 в C# на логи?** Разбираем по каналам:

### Логи = перенаправленный stdout/stderr

Writer и Stat запускаются фоново (`run_Writer.ps1` / `run_Stat.ps1`) с
`Start-Process ... -RedirectStandardOutput logs/writer.stdout.log
-RedirectStandardError logs/writer.stderr.log` (см.
[`run_Writer.ps1`](../src/Writer/run_Writer.ps1:204)). `Microsoft.Extensions.Logging`
пишет обычный вывод через `Console` (console logger provider), который и
перенаправляется в файл.

Значит **кодировка консольного вывода = кодировка файла логов**. Если C# не
выставит UTF-8, бинарник стартует с `Console.OutputEncoding = CP866`, и в файл
уйдут байты CP866 → «кракозябры».

Именно поэтому Writer и Stat **уже** содержат лечение на старте:

- [`ArtasWriter.Worker/Program.cs`](../src/Writer/ArtasWriter.Worker/Program.cs:13) —
  `Console.OutputEncoding = Encoding.UTF8;` (в `try/catch (IOException)`;
  при полной отвязке от консоли исключение гасится).
- [`Stat.Worker/Program.cs`](../src/Stat/Stat.Worker/Program.cs:13) — то же самое.

Проверка [`logs/writer.stdout.log`](../logs/writer.stdout.log:2) — кириллица
корректна:

```
info: ArtasWriter.Worker[0]
      Health-эндпоинты: http://localhost:8080/health и http://localhost:8080/exit
      Запуск Writer, старт: 10/14/2026 05:41:44
      PostgreSQL доступен — соединение восстановлено
```

Reader (GUI + `--check-db`) до правки этого лечения **не имел** — только он и
страдал (в консоли, при `-CheckDb`). После добавления
`Console.OutputEncoding = UTF8` в
[`ArtasChart.App/Program.cs`](../src/Reader/ArtasChart.App/Program.cs:31) вывод
стал корректным.

### А что с прямыми логами в файл (Serilog/File sink)?

Если логгер пишет **напрямую в файл** (свой `FileStream`/`StreamWriter` с явной
кодировкой), `Console.OutputEncoding` на него **не влияет** — там кодировка
задаётся отдельно при открытии потока/синка. Но в текущей архитектуре Writer/Stat
задействован **console logger + redirect**, поэтому на логи влияет именно
`Console.OutputEncoding`.

### Итог по логам

| Канал | Зависит от `Console.OutputEncoding`? | Статус |
|---|---|---|
| `stdout`/`stderr` → `logs/*.log` (redirect) | **Да** | Writer/Stat — UTF-8 уже выставлен, логи корректны |
| Reader CLI (`--check-db`) в консоль | **Да** | Добавлено в `Program.cs` Reader |
| Прямой file-sink (если появится) | Нет (кодировка задаётся в синке) | — |
| Loki через Promtail | читает файл как есть (UTF-8) | зависит от файла выше |

Практически: **да, кодировка влияет на логи** в текущей схеме (redirect),
поэтому выставление UTF-8 в C# — правильное решение, применённое во всех
исполняемых проектах.

## Нужна ли кодировка в самих `.ps1`?

Короткий ответ: **внутри `.ps1` настраивать кодировку не нужно** (и почти
бесполезно), кроме одного сценария — когда скрипт запускается **отдельным
процессом** и вы сами хотите, чтобы он «лечил» себя без внешнего префикса.

Проверено экспериментально на временных скриптах.

### Тест A — `.ps1` без ручной настройки, запуск `pwsh -File` (без префикса)

```
pwsh -NoProfile -ExecutionPolicy Bypass -File "scripts/_enc_ps1test.ps1"
```
```
[ps1] Без ручной настройки, OutputEncoding = cp866
[ps1] ��ਫ��� �� Write-Host: �ਢ��, 𦨪, �㪠, 񫪨.
[ps1] ��ਫ��� �� Write-Output: �஢�ઠ ��裡
```

### Тест B — тот же `.ps1`, но С ручной установкой UTF-8 в начале

```
pwsh ... -File "scripts/_enc_ps1test.ps1" -SetEnc
```
```
[ps1] Установил кодировку вручную
[ps1] Кириллица из Write-Host: Привет, Ёжик, щука, ёлки.
[ps1] Кириллица из Write-Output: Проверка Связи
```

Вывод: **отдельный процесс** `pwsh -File` открывает свой консольный handle,
поэтому ручная установка UTF-8 внутри скрипта работает.

### Тест C — влияние BOM в исходнике

Сравнивались два одинаковых файла — UTF-8 без BOM и UTF-8 с BOM — оба запущены
через `pwsh -File` (без префикса):

```
[nobom]   ��ப��� ���ࠫ �� ��室����: �ਢ��, 𦨪, �㪠.
[withbom] ��ப��� ���ࠫ �� ��室����: �ਢ��, 𦨪, �㪠.
```

Оба варианта искажены **одинаково** → **BOM не влияет** на кодировку
**вывода**. (BOM важен для корректного **чтения** самого исходника
PowerShell-ом — чтобы байты кириллических литералов декодировались как UTF-8, —
но на кодировку записи в консоль/файл он не влияет.)

### Тест D — вложенный `.ps1` через `&` (см. Тест 2 выше)

Если родитель в CP866, вложенный `.ps1` битый **независимо** от того, ставит ли
он кодировку у себя. Настройка внутри вложенного скрипта в этом случае
**бесполезна** (общий handle того же хоста).

### Итог: нужна ли кодировка в `.ps1`?

| Сценарий | Настройка внутри `.ps1` | Почему |
|---|---|---|
| Запуск под внешним UTF-8-префиксом | **Не нужна** | наследует `utf-8` от родителя |
| Вложенный через `&` в том же хосте | **Не помогает** | общий handle, кодировка уже зафиксирована |
| Отдельный процесс `pwsh -File`, нужен «самолечащийся» скрипт | **Работает** | новый консольный handle |

**Практическое правило для проекта:** настраивать кодировку **один раз — во
внешнем вызове** (UTF-8-префикс `pwsh -Command "...chcp 65001... & '<script>'"`).
Дублировать настройку в каждом `.ps1` не требуется; она оправдана только если
скрипт спроектирован запускаться автономно (отдельным процессом) и должен
работать даже без префикса.

Дополнительно: файлы кириллических `.ps1` в репозитории хранятся как
**UTF-8 with BOM** (проверено для [`run_Reader.ps1`](../src/Reader/run_Reader.ps1:1)
и [`run_Writer.ps1`](../src/Writer/run_Writer.ps1:1)) — это обеспечивает
корректное **чтение** литералов, но, как показал Тест C, **не** заменяет
настройку кодировки вывода.

## Практические выводы (правило)

- Кириллицу гарантирует только **UTF-8-префикс у самого внешнего вызова**
  (`pwsh -Command "...chcp 65001... & '<script>.ps1'"`).
- Вложенные `.ps1`, вызываемые через `&`, **наследуют** режим консоли
  родителя — их собственная настройка `[Console]::OutputEncoding` бесполезна.
  Настраивать кодировку нужно **один раз — на входе**.
- Для дочерних **.NET-приложений** вывод лечится **только в C#-коде**.
- Настройка родителя (chcp/`$OutputEncoding`) и настройка C# — две
  независимые вещи; нужны обе, если нужен полностью корректный вывод.

# План: WSL перезагружается при выходе последнего пользователя

## Проблема

Пользователь заметил, что WSL «перезагружается», когда выходят все пользователи.
Косвенные признаки:

```
PS C:\Users\Dionis> wsl docker ps
artas_postgres   Up 2 seconds (health: starting)   <- контейнер только что перезапущен
qdrant-roo       Up 4 seconds

PS C:\Users\Dionis> wsl -d Ubuntu -e uptime
 16:54:49 up 0 min,  1 user,  load average: 2.52

PS C:\Users\Dionis> wsl -d Ubuntu -e uptime      # повторно, через минуту
 16:58:02 up 0 min,  1 user,  load average: 1.04   <- ВМ снова перезапустилась
```

**Ключевой симптом:** `up 0 min` при **каждом** запуске `wsl` (даже без закрытия сеанса).
Значит новое подключение `wsl.exe` не «подключается к живой ВМ», а **пересоздаёт её с нуля**.

---

## ⚡ УТОЧНЕНИЕ ПРИЧИНЫ (08.10.2026, после детального анализа journal)

Изначальная гипотеза «логаут Windows» — **неверна**. Autologon выключен
(`AutoAdminLogon=0`), консольная сессия `dionis` (console ID 1) держится с 12:43 и не
закрывается. Тем не менее `System is powering down` происходит **каждые 15-30 секунд**.

### Что показывают логи (boot -1, 17:55-17:57)

```
17:55:16 login[973]:  session opened for user root      <- интерактивный LOGIN
17:55:16 login[1027]: ROOT LOGIN on '/dev/pts/1'         <- реальный вход (getty)
17:55:17 login[1049]: session opened for user myuser
17:55:38 session closed for user root                    <- выход
17:55:38 systemd-logind: System is powering down          <- СРАЗУ poweroff
17:55:44 ... новый login myuser
17:56:00 System is powering down                          <- снова poweroff
```

Характер сессий — **полноценные `login`-сессии через getty** (`login[...]`,
`ROOT LOGIN on /dev/pts/1`), а не фоновые процессы. Их порождали **вызовы `wsl.exe`**
(в т.ч. диагностические команды `wsl -d Ubuntu ...`, `wsl docker ps`, `wsl -e uptime`).

### Истинная причина

**Каждый вызов `wsl.exe` (без долгоживущей полезной нагрузки) поднимает ВМ и гасит её
при своём завершении.** Если в дистрибутиве в этот момент нет другого активного клиента,
`wsl.exe` при выходе инициирует `System is powering down`. Отсюда:

- `uptime` показывает `up 0 min` почти всегда — ВМ поднимается на время команды;
- контейнеры в `Up N seconds (health: starting)` — были остановлены при прошлом poweroff,
  подняты автозапуском при новом boot;
- циклы раз в 15-30 сек = периодические одиночные вызовы `wsl` (мониторинг/опрос).

Это **не сбой и не «перезагрузка»** — это штатное поведение WSL2: дистрибутив живёт
ровно столько, сколько длится клиентский сеанс.

### Демонстрация: «редкие вызовы → перезапуск, частые → нет»

Наблюдаемый лог пользователя (серия `wsl docker ps` подряд):

| Вызов | Uptime контейнера | Что произошло |
|-------|-------------------|---------------|
| 1 | `Up 14 sec` | старый boot, между вызовами была пауза |
| 2 | `Up < 1 sec` | **ВМ погасла в паузе и поднялась заново** (новый boot) |
| 3 | `Up 3 sec` | вызовы идут подряд — ВМ держится |
| 4 | `Up 5 sec` | +2 сек, держится |
| 5 | `Up 7 sec` | +2 сек, держится |
| 6 | `Up 16 sec` | +9 сек, держится |

Из journal в этот момент:
```
18:08:31  System is powering down      <- ВМ погасла (graceful stop PG) в паузе
18:09:04  autostart                     <- поднялась заново
```

**Механизм:** WSL гасится, когда завершается последний клиент `wsl.exe` и нет нового.
- **Редкие вызовы с паузами** → в каждую паузу ВМ гаснет → следующий вызов = новый boot
  («перезапуск»).
- **Частые вызовы подряд** → клиенты перекрываются, ВМ не успевает погаснуть → uptime
  растёт монотонно, перезапусков нет.

Аналогия: датчик движения на лампочке — ходишь = свет горит, стоишь дольше таймаута =
гаснет и включается заново при следующем шаге.

### Что делать (практические шаги)

1. **Держать фоновый клиент WSL.** ⚠️ Обычный `wsl -d Ubuntu` **занимает терминал** —
   для выхода нужно набрать `exit`, что завершает клиент и гасит ВМ. Вместо этого
   запускайте удержание как **фоновый скрытый процесс**:

   ```powershell
   .\scripts\wsl_hold.ps1          # запустить удержание (фоном, не занимает окно)
   .\scripts\wsl_hold.ps1 -Status  # проверить
   .\scripts\wsl_hold.ps1 -Stop    # остановить
   ```

   Скрипт запускает `wsl.exe -d Ubuntu -e sleep infinity` в фоне через `Start-Process
   -WindowStyle Hidden`. Проверено:
   - окно PowerShell остаётся свободным;
   - обычный доступ `wsl -d Ubuntu` / `wsl docker ps` **не блокируется** (exit=0);
   - uptime контейнеров накапливается (`Up About a minute`), перезапусков нет.

   Проверка эффекта: `wsl -d Ubuntu -e uptime` — время должно накапливаться, а не `0 min`.

   **✅ ВЫПОЛНЕНО (08.10.2026 18:12):** скрипт запущен, удержание активно.
   Результат проверки:
   ```
   OK: удержание запущено (PID: 10096, 14564, 16232).
   wsl docker ps -> artas_postgres Up About a minute (healthy)   # uptime накапливается
   wsl -d Ubuntu -e uptime -> 18:12:55 up 1 min                 # exit=0, доступ не сломан
   ```
   Ключевое отличие от отклонённого варианта с задачей S4U/SYSTEM: клиент запущен
   **в той же интерактивной сессии**, поэтому НЕ монополизирует дистрибутив — обычный
   доступ сохраняется.

   **✅ АВТОЗАПУСК ПРИ ВХОДЕ (08.10.2026 18:23):** удержание добавлено вторым действием
   в задачу `AutoStart WSL Ubuntu` — теперь стартует автоматически после входа в Windows.
   Регистратор: [`scripts/register_wsl_hold_task.ps1`](scripts/register_wsl_hold_task.ps1).
   Проверено: после запуска задачи удержание поднялось (`Result=0`, PID 12180/8476/10396),
   доступ `wsl docker ps` не сломан (`exit=0`).

   > ⚠️ Важные детали реализации (все выяснены экспериментально):
   > 1. Задача должна запускать **`pwsh.exe` (PowerShell 7)**, а НЕ `powershell.exe` (5.1):
   >    Windows PowerShell 5.1 читает `.ps1` без BOM как ANSI и падает на кириллице
   >    (`Result=1`). Регистратор указывает полный путь
   >    `C:\Program Files\PowerShell\7\pwsh.exe`.
   > 2. [`scripts/wsl_hold.ps1`](scripts/wsl_hold.ps1) запускает клиент через
   >    **`Start-Process -WindowStyle Hidden`** — окна консоли НЕ создаёт
   >    (`MainWindowHandle=0`), процесс переживает завершение скрипта/задачи.
   >    ❌ **НЕ использовать WMI `Win32_Process.Create`:** он создаёт ВИДИМОЕ окно
   >    консоли `wsl.exe`; при его закрытии пользователем удержание обрывается.
   > 3. Principal задачи переключён на `Interactive` (было `Password`) — пароль не нужен,
   >    клиент создаётся в интерактивной сессии.

2. **Найти и убрать частые одиночные `wsl`-вызовы.** Каждый такой вызов = подъём+гашение
   ВМ. **Проверено:** рабочие сервисы ([`src/Writer`](src/Writer), [`src/Stat`](src/Stat))
   `wsl` НЕ вызывают — они подключаются к PostgreSQL напрямую через `localhost:5432`
   (см. [`ArtasCore`](src/Core/ArtasCore) `DbConfig`). `wsl`-вызовы есть только
   в задачах планировщика/диагностических командах. Источник 15-30-секундных циклов —
   ручные/периодические `wsl`-вызовы (в т.ч. мониторинг, `wsl docker ps` вручную, задачи).
   Рекомендация: не вызывать `wsl` в цикле; для доступа к БД использовать
   `127.0.0.1:5432` напрямую.

3. **Если нужна работа 24/7 без залогиненного пользователя** — только полноценная ВМ
   (Hyper-V/VMware). WSL архитектурно гасится без активного клиента.

### Что НЕ работает (проверено экспериментами)

- ❌ `sleep infinity` внутри ВМ (systemd-сервис) — не удерживает.
- ❌ Сервис/задача-удержание — либо не удерживает, либо монополизирует дистрибутив
  (ломает интерактивный доступ `wsl -d Ubuntu` → «Отказано в доступе»).
- ❌ Отключение autologon — не влияет (проблема не в логауте; `AutoAdminLogon=0` и так).
- ❌ **Включение autologon — НЕ решит проблему** (частый вопрос). Причина не в логауте:
  консольная сессия пользователя держится непрерывно, а poweroff идёт при завершении
  `wsl`-клиента. Autologon хранит пароль в открытом виде в реестре
  (`HKLM\...\Winlogon\DefaultPassword`) — снижение безопасности без пользы для этой задачи.

## Анализ источников проблемы (5–7 гипотез)

| № | Гипотеза | Проверка | Вердикт |
|---|----------|----------|---------|
| 1 | `wsl-docker-graceful-shutdown.service` с `DefaultDependencies=no` + `Before=shutdown.target` останавливается при каждой смене target | journal: сервис виден в списке, `ExecStop` срабатывал много раз | **Возможно, но вторично** |
| 2 | **Windows-задача `AutoStart WSL Ubuntu` с триггером Logon + `wsl -d Ubuntu -e ...`** | `Get-ScheduledTask` → задача существует, триггер Logon, Action `wsl -d Ubuntu -u root -e systemctl is-system-running` | **✅ ПОДТВЕРЖДЕНО — первопричина** |
| 3 | `Artas_SafeShutdown` (EventID 1074) гасит PG перед shutdown Windows | существует, State=Ready, срабатывает только при реальном shutdown | Вторично (полезен) |
| 4 | Задача `Artas_PgMonitor` создаёт цикл restart | State=**Disabled** | Не влияет |
| 5 | WSL idle timeout / vmIdleTimeout гасит ВМ без сеансов | в `.wslconfig` нет `vmIdleTimeout`; но есть механизм Windows «остановка неиспользуемой ВМ» | Усиливает гипотезу 2 |
| 6 | `wsl-artas-autostart.service` сам перезапускает контейнеры | это стартовый сервис, срабатывает только при boot ВМ | Следствие, не причина |
| 7 | OOM/нехватка ресурсов гасит ВМ | memory=8GB, processors=4; в journal нет OOM-kill | Не подтверждено |

### Вывод: первопричина — механизм жизненного цикла WSL

WSL2 автоматически **останавливает виртуальную машину, когда в ней не остаётся ни одного
активного сеанса/процесса** (idle VM shutdown / no-session teardown Windows). При этом:

1. Windows гасит util-linux ВМ → systemd выполняет `wsl-docker-graceful-shutdown.service`,
   который делает `docker stop -t 60 artas_postgres` → **PG останавливается**
   (записи в `/var/log/artas-graceful-stop.log` в 14:38, 14:41, 14:46, 16:46, 16:55).
2. Через несколько десятков секунд **Windows-задача `AutoStart WSL Ubuntu`** (или ручной
   `wsl docker ps`) **поднимает ВМ заново** → systemd запускает
   `wsl-artas-autostart.service` → `docker compose up -d postgres`
   (записи в `/var/log/artas-autostart.log`).
3. Каждый запуск `wsl.exe` в отсутствие сеанса **создаёт новый boot** (uptime = 0),
   что и выглядит как «перезагрузка».

### Разбор задачи `AutoStart WSL Ubuntu`

```xml
<Triggers>
  <LogonTrigger>          <!-- триггер: вход любого пользователя -->
    <Delay>PT30S</Delay>
    <UserId>DESKTOP-VCQ4UJI\Dionis</UserId>
  </LogonTrigger>
</Triggers>
<Actions>
  <Exec>
    <Command>wsl</Command>
    <Arguments>-d Ubuntu -u root -e systemctl is-system-running</Arguments>
  </Exec>
</Actions>
```

Задача **запускает `wsl` через 30 секунд после входа в систему**. Команда безобидна
(`systemctl is-system-running`), но сам факт запуска `wsl.exe` **инициирует старт ВМ**,
если она была погашена после выхода предыдущего пользователя. Именно поэтому:

- после логаута ВМ гаснет (graceful stop),
- при следующем логоне задача стартует ВМ заново (uptime=0),
- контейнеры «Up N seconds (health: starting)».

**Цикл logoff → VM shutdown → задача/ручной wsl → VM boot** повторяется, и это
воспринимается как «WSL перезагружается при выходе всех пользователей».

## Диагностический вывод (для подтверждения)

Признаки указывают, что «перезагрузка» — это **не сбой, а штатное поведение**
жизненного цикла WSL2 в сочетании с задачей `AutoStart WSL Ubuntu`:

- Windows останавливает WSL-ВМ, когда пропадает последний сеанс/потребитель
  (нет активных `wsl.exe`, сеансов, VS Code, открытых портов с активной нагрузкой).
- Задача `AutoStart WSL Ubuntu` (LogonTrigger) и любой ручной `wsl <cmd>` поднимают
  ВМ обратно за считанные секунды → uptime=0, контейнеры в состоянии `health: starting`.

Если это поведение нежелательно (процессам Artas нужна непрерывная работа),
ВМ нельзя «отпускать» в idle — нужно удерживать её запущенной.

```powershell
# Зафиксировать текущее время старта ВМ
```

## ШАГ 2: Устранить причину (варианты по возрастанию надёжности)

### Вариант A: Отключить/пересмотреть задачу `AutoStart WSL Ubuntu`

Если задача нужна только чтобы «прогреть» WSL после логона — этого мало, она не держит ВМ.
Если она не критична:

```powershell
Disable-ScheduledTask -TaskName 'AutoStart WSL Ubuntu'
# или полностью:
# Unregister-ScheduledTask -TaskName 'AutoStart WSL Ubuntu' -Confirm:$false
```

> ВНИМАНИЕ: это уберёт автозапуск WSL после входа, но НЕ удержит ВМ от idle-гашения.

### Вариант B: Удерживать WSL-ВМ запущенной при залогиненном пользователе

**✅ Рабочее решение (проверено): [`scripts/wsl_hold.ps1`](scripts/wsl_hold.ps1).**
Запускает фоновый клиент `wsl.exe -d Ubuntu -e sleep infinity` через `Start-Process
-WindowStyle Hidden`. Не занимает терминал, не ломает доступ, удерживает ВМ.

```powershell
.\scripts\wsl_hold.ps1          # запустить
.\scripts\wsl_hold.ps1 -Stop    # остановить
```

Ограничение: фоновый клиент живёт до логаута Windows (после входа запустить снова).

> ### ⚠️ Что НЕ работает (проверено экспериментами — см. разделы ниже)
>
> - ❌ **systemd-сервис внутри ВМ** (`wsl-keepalive.service`, `sleep infinity`): ВМ всё
>   равно гасится при завершении клиента `wsl.exe`. Эксперимент 1 — не удерживает.
> - ❌ **Windows-задача от SYSTEM/S4U** (`Artas_WSL_Keepalive`): дистрибутив
>   монополизируется — интерактивный доступ `wsl -d Ubuntu` даёт «Отказано в доступе».
>   Эксперимент 2 — ломает работу.
> - ❌ **Клиент в интерактивной сессии напрямую** (`wsl -d Ubuntu` в окне): занимает
>   терминал, `exit` гасит ВМ. Поэтому используется фоновый запуск (см. выше).
>
> Артефакты неработающих подходов удалены из репозитория.

> ### Проверка решения
>
> ```powershell
> .\scripts\wsl_hold.ps1 -Status   # удержание активно + uptime растёт
> wsl docker ps                    # контейнеры 'Up N min', без 'Up 0 sec'
> ```

### Вариант C: Отключить autostart-сервис Artas и полагаться на `restart: unless-stopped`

Если ВМ всё равно гасится, `docker stop` при выключении заставляет Docker считать
остановку ручной. Можно вместо `docker stop` использовать более мягкое завершение,
чтобы `restart: unless-stopped` отработал при следующем boot ВМ.

### Обоснование

1. Удержать дистрибутив между логаутами штатными средствами **невозможно** (доказано
   двумя экспериментами).
2. Текущая связка **уже гарантирует сохранность данных**:
   - [`wsl-docker-graceful-shutdown.service`](db/init-scripts/wsl-docker-graceful-shutdown.service) —
     при выключении ВМ `docker stop -t 60` → PostgreSQL делает checkpoint, WAL чистый;
   - [`wsl-artas-autostart.service`](db/init-scripts/wsl-artas-autostart.service) —
     поднимает контейнеры при следующем boot ВМ.
3. Издержка — простой контейнеров, пока нет залогиненного пользователя. Для сценария
   Artas это приемлемо.

### Что сделано в рамках решения

- Неработающие артефакты удалены из репозитория: `wsl-keepalive.service`,
  `install_wsl_keepalive.ps1`, `register_wsl_keepalive_task.ps1`.
- Создан [`scripts/wsl_hold.ps1`](scripts/wsl_hold.ps1) — фоновое удержание ВМ
  (проверено, работает без побочных эффектов).
- В [`db/POSTGRES_WSL_SETUP.md`](db/POSTGRES_WSL_SETUP.md) добавлены: раздел про поведение
  WSL при выходе последнего пользователя и раздел «Как удержать ВМ».
- Проверено здоровье PostgreSQL (pg_is_in_recovery, count).

## ❌ ПРОВЕРЕНО И НЕ РАБОТАЕТ: `wsl-keepalive.service` (sleep infinity)

Гипотеза «фоновый процесс в ВМ удержит её от выключения» **опровергнута экспериментом**.

### Что было сделано

Создан и установлен сервис:
- [`db/init-scripts/wsl-keepalive.service`](db/init-scripts/wsl-keepalive.service) —
  `ExecStart=/bin/sleep infinity`, `Restart=always`;
- [`scripts/install_wsl_keepalive.ps1`](scripts/install_wsl_keepalive.ps1) — установщик.

Сервис успешно поднялся (`active (running)`, `Main PID 1091 (sleep)`, `enabled`).

### Результат: НЕ помогло

После установки сервиса ВМ всё равно перезапустилась. Проверка:

```
 17:20:58 up 2 min      <- после выхода 'myuser' сеанс закрылся, ВМ ушла в shutdown
...
 17:21:41 up 3 min      <- новый boot, контейнеры 'Up 3 seconds'
```

`journalctl --list-boots` продолжает расти (boot -2, -1, 0 добавляются минутами позже).

### Доказательство первопричины (journal boot -1)

```
17:02:56 unknown: Operation canceled @p9io.cpp:258 (AcceptAsync)   <- WSL Plan9 teardown
17:02:56 systemd-logind[215]: System is powering down.             <- logind гасит систему
17:02:56 systemd[1]: Stopping Session 1 of User myuser...
17:02:56 systemd-logind[215]: Session 1 logged out. Waiting for processes to exit.
17:02:56 systemd-logind[215]: Removed session 1.
17:02:59 systemd[1]: Reached target System Shutdown.
```

### Истинная причина

WSL **сам инициирует выключение дистрибутива**, когда закрывается **последний клиент
`wsl.exe`** (сеанс/терминал). Через Plan9-канал (`p9io.cpp`) WSL посылает в дистрибутив
команду poweroff, systemd-logind выполняет `System is powering down` и **гасит всю
систему**, игнорируя любые фоновые процессы, включая `sleep infinity`.

Ключевой факт: **дистрибутив WSL живёт ровно столько, сколько в нём есть активный
клиентский сеанс `wsl.exe`**, а не «пока есть процессы». Поэтому сервис внутри ВМ
принципиально не может удержать дистрибутив. Это архитектурное поведение WSL2 2.6.3,
а не сбой.

## Эксперимент 2: Windows-задача `Artas_WSL_Keepalive` — ❌ блокирует доступ

Проверен следующий вариант: держать клиент `wsl.exe` со стороны Windows через задачу
Планировщика, в трёх режимах logon. Скрипт: [`scripts/register_wsl_keepalive_task.ps1`](scripts/register_wsl_keepalive_task.ps1).

Гипотеза: клиент в отдельной logon-сессии удержит ВМ и не умрёт при логауте.

### Результаты по режимам

| Режим (`-Mode`) | Задача | Клиент `wsl.exe` | Интерактивный доступ `wsl -d Ubuntu` |
|-----------------|--------|------------------|--------------------------------------|
| `SYSTEM` | создана, `Result=1` | **не создан** | — (дистрибутив недоступен из сессии 0) |
| `S4U` | `State=Running` | **создан** (PID 16548/14308/13772) | **❌ «Отказано в доступе» (exit=1)** |
| `InteractiveOnly` | — | удерживает | ✅ не блокирует (но умирает при логауте) |

### Ключевое наблюдение

При активной S4U-задаче обычная работа с WSL **ломается**:
```
PS> wsl -l -v
Отказано в доступе.
PS> wsl -d Ubuntu -e uptime
Отказано в доступе.   (exit=1)
```
Сразу после остановки задачи доступ восстанавливается (`Ubuntu Running`, exit=0).

Причина: клиент `wsl.exe`, запущенный в **отдельной logon-сессии** (даже от того же
пользователя через S4U), **монополизирует дистрибутив**. WSL допускает одну
сессию-владелец дистрибутива, и интерактивная сессия пользователя теряет доступ.

Проверено: клиент `wsl.exe`, запущенный **в той же интерактивной сессии**
(`Start-Process wsl -d Ubuntu -u root -e sleep 3600`), доступ **НЕ блокирует**
(`wsl -d Ubuntu -e uptime` → exit=0). То есть конфликт вызывает именно чужая logon-сессия.

Задача удалена, система возвращена в рабочее состояние.

## Итоговый вывод: штатными средствами удержать ВМ между логаутами без побочных эффектов НЕЛЬЗЯ

Совокупность экспериментов:

| Способ удержания | Удерживает между логаутами? | Ломает интерактивный доступ? |
|------------------|------------------------------|------------------------------|
| Сервис в ВМ (`sleep infinity`) | ❌ нет | нет |
| Клиент в задаче SYSTEM/S4U | ✅ да | ❌ **да** |
| Клиент в интерактивной сессии | ❌ нет (умирает при логауте) | нет |

**Фундаментальное ограничение WSL2:** дистрибутив живёт, пока есть активный клиент
`wsl.exe` **в текущей интерактивной сессии**. Клиент из чужой logon-сессии монополизирует
дистрибутив. Поэтому полностью решить задачу «работать без залогиненного пользователя»
штатными средствами WSL нельзя.

## Реальные варианты (в порядке практичности)

### Вариант A (рекомендуется): принять самовосстанавливающееся поведение

Текущая связка **уже корректно обрабатывает** циклы:
- при выключении ВМ [`wsl-docker-graceful-shutdown.service`](db/init-scripts/wsl-docker-graceful-shutdown.service)
  делает `docker stop -t 60` — **чистый WAL, повреждения БД нет**;
- [`wsl-artas-autostart.service`](db/init-scripts/wsl-artas-autostart.service) возвращает
  контейнеры при следующем подъёме;
- задача `AutoStart WSL Ubuntu` поднимает ВМ после входа.

Единственная издержка — простой контейнеров, пока нет залогиненного пользователя.
Если непрерывная работа 24/7 не требуется — это оптимальный выбор.

### Вариант B: сервис Windows (не задача) с `wsl.exe` под пользователем

Запускать удержание как **Windows-службу** (например через [NSSM](https://nssm.cc/) или
`sc.exe`), работающую от локальной учётной записи пользователя. Это может обойти
монополию logon-сессии, т.к. служба работает в session 0 иначе, чем задача. **Требует
отдельной проверки** (в текущем проекте не проверялось).

> ВАЖНО: проверить, что при этом интерактивный доступ `wsl -d Ubuntu` продолжает работать.

### Вариант C: держать пользователя залогиненным

Если критична непрерывность — использовать сессию, которая не завершается
(autologon + отключение экрана), тогда удержание в интерактивной сессии сохраняется.

### Вариант D: перейти на полноценную VM (Hyper-V/VMware)

Если нужна работа без залогиненного пользователя 24/7, WSL архитектурно не подходит —
следует использовать ВМ с отдельной службой.

## Приложение: почему `sleep infinity` не удерживает WSL

- Голый `wsl -d Ubuntu -e sleep infinity` из интерактивного сеанса **умирает вместе с
  сеансом** — ровно при выходе пользователя.
- Даже **сервис внутри ВМ** (`wsl-keepalive.service`) **не удерживает дистрибутив**, потому
  что WSL гасит дистрибутив по исчезновению клиента `wsl.exe` (Plan9 `Operation canceled`,
  `System is powering down`), а не по наличию процессов.
- Клиент `wsl.exe` со стороны Windows удерживает, но если он в **чужой logon-сессии** —
  монополизирует дистрибутив и ломает интерактивный доступ (эксперимент 2).
